Patch and chat workflow
- Every implementation, fix, diagnostic, checkpoint, cleanup, documentation
  update and boundary is one complete downloadable sequential Python file.
  The assistant does not place or execute numbered patches on HomeLab unless
  explicitly asked.
- Filenames begin with the number, never patch_. Failed user-run scripts
  consume their number. Successful scripts print exactly `Everything PASS`.
- Headings are `Patch N - Browser Test` or `Patch N - Fix Only`.
- Browser-test source remains unstaged/uncommitted until explicit approval,
  followed by a separate checkpoint/commit/push script.
- Chat 15 is `Chat 15: Project Lifecycle Completion`, owns 397-426 and ends
  at boundary Patch 426.
- Chat 16 is `Chat 16: Backup and Restore Foundation`, owns 427-456 and
  Patch 456 is its planned boundary.
- No next-chat starting-prompt file is created. The ready prompt is posted
  in chat only after a successful boundary.
- After two consecutive pre-write failures, repeated anchor mismatches or
  source uncertainty, the next patch is diagnostic-only and creates
  docs/diagonostic_*.md.

HomeLab-assisted safeguards
- Inspect exact Git/index state, source hashes, logs, deployment, OpenAPI,
  bundles and live SQLite before high-risk patches. Local source and newest
  handoff/diagnostic are authoritative.
- Generate transforms in memory before backup/write. Prefer exact hashes,
  scoped structures and semantic validation over brittle adjacency.
- Backups: /projects/Part Pilot/fixes/backups/
- Logs: /projects/Part Pilot/fixes/logs/ and ignored by Git.
- Application patches run git diff --check, Python/TypeScript validation,
  Docker build/deploy, Alembic/protected API/SPA marker checks, complete
  copied-database smoke and live-data preservation.
- Failure output includes phase, exception, actual command or in-memory
  transform, rollback result, final Git state and log path.
- Checkpoints stage explicit allowlists, validate staged diff, push main,
  fetch and verify local HEAD equals origin/main.
- Keep this memory at or below 8,000 characters.

Inventory and fixture safety
- Never assume an empty database. Preserve users, catalogues, inventory,
  Projects, Reservations, movements, audits and settings.
- Use unique manifest-owned fixtures and clean up only recorded IDs.
- Six realistic Patch 401 parts remain intentionally in the test database.
  Manifest: /projects/Part Pilot/fixes/logs/patch_401_test_fixture_manifest.json
- The user plans to reset before production use. Do not silently remove
  fixtures or History.
- SQLite integrity and foreign-key checks must pass.
