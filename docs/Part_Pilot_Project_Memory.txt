Patch and chat workflow
- Every change is one complete sequential Python patch file under fixes/.
- The assistant may place scripts directly there; the user executes them.
- Filenames begin with the number, never patch_. Failed user-run scripts consume
  their number. Successful scripts end with exactly `Everything PASS`.
- Use headings `Patch N - Browser Test` or `Patch N - Fix Only`.
- Browser instructions stay outside scripts. Browser-test source stays unstaged
  and uncommitted until explicit approval, then a separate checkpoint commits
  and pushes it.
- Chat 14 is `Chat 14: Projects Foundation`, owns Patch 366-395, and Patch 395
  is its planned boundary. No next-chat prompt files are created.

Mandatory HomeLab-assisted method
- Before every patch, inspect exact local Git/index state, source, logs,
  deployment, HTTP contracts and SQLite values through HomeLab. Local source is
  authoritative; never assume GitHub represents pending work.
- Generate proposed targets under /tmp and validate them twice. Overlay exact
  targets onto a clean repository copy; run TypeScript/Vite and Docker builds,
  production-bundle checks and the complete smoke suite against a copied DB.
- Only then package the exact tested bytes into the numbered script. Avoid
  execution-time brittle source-anchor discovery.
- Scripts validate repo, branch, origin, HEAD/origin equality, index, pending
  allowlists, exact hashes, prerequisites and successful prior logs before
  backup/write. Show clear [X/N] phases.
- Back up every affected source file, SQLite and rollback image. Validate
  Alembic, full smoke, protected APIs, SPA routes, runtime markers and logical
  DB preservation. Failure output includes phase, exception, command, useful
  output, rollback result, final Git state and log path.
- After two consecutive pre-write failures, repeated anchor mismatches or local
  source uncertainty, stop and issue a diagnostic-only patch.
