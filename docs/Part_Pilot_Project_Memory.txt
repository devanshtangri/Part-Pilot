Patch workflow
- Every implementation/fix/diagnostic/docs/checkpoint/commit/push/boundary/handoff is one sequential Python file under `fixes/`; filename begins directly with patch number. Failed executed scripts consume numbers. Success final line exactly `Everything PASS`.
- User normally runs numbered patches. Assistant may run one only when explicitly asked to execute that exact patch; then run the exact command once and return raw terminal output only, without diagnosis/retry/extra commands.
- Before writes validate repo/root, branch, origin, committed HEAD, exact index/source bytes, prerequisites and transforms. Avoid brittle whitespace anchors. Backups `fixes/backups/`; logs `fixes/logs/`; diagnostics `docs/diagonostic_*.md`.
- Browser-test app source remains uncommitted/unpushed until explicit user approval. Browser instructions stay outside patch scripts. After approval create a separate checkpoint/commit/push patch promptly.
- App patches: `git diff --check`, relevant Python compile, canonical Docker build, Alembic validation, copied-production/relevant complete smokes, protected APIs, SPA/runtime markers and real-data preservation. Rehearsals stay isolated from live source/deployment.
- Stage only intended allowlist; verify staged diff; push main, fetch and verify local HEAD == origin/main. Documentation-only checkpoints while app source is pending require exact allowlist/proof app bytes unchanged.
- After two consecutive pre-write failures/repeated anchor mismatches/uncertain pending source, diagnostic-only next.
- Origin validation must match the verified configured remote identity; Patch 767 proved that freezing an equivalent HTTPS spelling when local origin is SSH causes a false preflight failure. Durable failure evidence lives in the patch log, not terminal-only prose.
- Repo memory target <=20,000 characters. Treat newest handoff + local repo state as authoritative for volatile hashes/runtime/pending state.
- Patch delivery order: heading; file/path; SHA-256; concise scope/status; exact run command; expected final line `Everything PASS`. For AI/MCP browser tests always provide exact copy-paste prompts for the user to send.

Product/UI rules

MCP/OAuth/direct access
- OAuth discovery/DCR/PKCE/consent/token/refresh/revocation and stateless `/mcp`; real Claude/ChatGPT flows verified. OAuth scope challenges advertise enabled read/write categories; existing tokens never silently gain `mcp:write`.
- Named direct clients support Bearer/custom-header/trusted-network authentication. No-auth is off by default, typed-confirmed, read-only and lower precedence than explicit credentials/trusted networks.
- Global individual-tool permissions + per-client deny ceilings + server/read/write category gates are enforced at discovery and call time. Live permission booleans are mutable configuration.
- Safeguarded writes reuse canonical services and require server/write/global/client/scope ceilings, active Operator-or-higher backing user, preview, short-lived one-time confirmation, idempotency/completed replay and state-drift rejection. No-auth stays read-only.
- Current guarded writes: `reserve_project`, `consume_reservation`, `cancel_reservation`, `adjust_part_quantity`, `create_part`, `update_part_metadata`, `soft_delete_part`, `restore_part`.
- `update_part_metadata` requires complete explicit editable metadata replacement, cannot change stock and freezes relevant catalogue/template dependencies without coupling confirmation to unrelated stock-only changes.
- `soft_delete_part` and `restore_part` use canonical recycle-bin services. Soft delete preserves quantities/reservations/fields/movements/history; restore checks deleted-state snapshot and part-number availability and returns the same record. Neither creates stock movement solely for lifecycle change. Permanent purge/hard delete/recycle-bin emptying is deliberately NOT exposed to MCP.
- History shows connected MCP client identity (e.g. Claude) while retaining backing Part Pilot user authority/accountability.
