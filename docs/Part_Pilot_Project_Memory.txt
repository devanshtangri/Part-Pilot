Patch workflow
- Every implementation, fix, diagnostic, cleanup, docs update, checkpoint,
  commit, push and handoff is one complete downloadable Python file.
- Never require manual edits.
- Use one sequential patch number. Once run it is consumed, even if it fails
  before writes; never reuse it.
- Filenames begin with the number, never `patch_`; filename and command match.
- Successful scripts end with exactly `Everything PASS`.
- Validate repo, branch, origin, committed HEAD, exact local source/index state,
  prerequisites and every transform in memory before backup/write.
- While browser-test source is uncommitted, local files and the newest committed
  diagnostic are authoritative; GitHub app source may be behind.
- Avoid whitespace/adjacency anchors. Scope transforms to verified functions,
  components or blocks and validate semantics, counts and reversal.
- Backups: /projects/Part Pilot/fixes/backups/
- Logs/reports: /projects/Part Pilot/fixes/logs/
- Diagnostic Markdown filenames start with exact prefix `diagonostic_`.
- Failure output includes phase, exception, actual failing command or
  `in-memory source transformation`, useful stdout/stderr, rollback result,
  final Git state and log path.
- Application changes run git diff --check, compile Python, build/deploy, verify
  Alembic, full smoke tests, protected APIs, SPA routes, markers and inventory;
  restore source/deployment on failure.

Diagnostic-first escalation
- After two consecutive pre-write failures, repeated anchor mismatches, or
  uncertainty about pending local source, stop implementation.
- The next sequential patch is diagnostic-only and inspects exact local Git
  state, index, deployment, database and relevant source.
- It creates fixes/logs/diagonostic_*.md with HEAD/origin, status/index state,
  hashes, markers, source excerpts, discovered shapes, anchor counts and a safe
  implementation plan.
- Commit/push diagnostic+memory with an explicit documentation-only allowlist
  while proving pending browser-test app bytes/index are unchanged.
- Do not resume implementation until the diagnostic passes, is committed and
  its report is inspected.

Browser workflow
- Never put browser instructions inside patch scripts.
- Terminal `Everything PASS` means automated checks only; browser steps follow
  separately when required.
- Keep browser-test source uncommitted/unpushed until explicit approval.
- Apply feedback in the next sequential script.
- After approval, issue a separate checkpoint/commit/push script promptly.

Git workflow
- Check local status/index before assuming GitHub is current.
- Commit small independently approved batches promptly.
- Documentation-only commits while app source is pending require a temporary
  index or explicit allowlist and proof app bytes/index are unchanged.
- Stage only intended files; verify staged set and staged diff --check.
- Push main, fetch and verify local HEAD equals origin/main.
